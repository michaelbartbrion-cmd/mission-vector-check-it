# Rebel Core telemetry contract

Status: development contract for Mission Vector Check It

Rebel Command is the Mission management/monitoring application. Rebel Core is the Mission-owned central data layer. This contract lets Vector-facing tools report health, usage, factual activity, plans, verified credits, suggestions, and reconciliation exceptions without moving management UI onto the daily Vector screen.

## Non-negotiable safety boundary

Telemetry is a side channel only.

- A telemetry outage must never block or alter Vector Scheduling, Vector Rebel, PPE checks, clicks, submits, or other operational workflows.
- Telemetry code must not add Vector writes.
- Never send passwords, cookies, session tokens, pairing secrets, keystrokes, arbitrary page dumps, or unrelated personal data.
- Never commit a live Rebel Core device token to GitHub.
- Pairing material stays in the authorized browser. Rebel Core stores only the SHA-256 hash of the device secret.
- Fail closed for telemetry authentication but fail open for the operational Vector tool: if reporting fails, the Vector tool continues normally.

## Pairing

The browser stores a private JSON payload generated by Rebel Command:

```json
{
  "endpoint": "https://<rebel-command-host>/functions/ingestTelemetry",
  "deviceId": "<device-id>",
  "token": "<random-device-secret>"
}
```

The token is sent only in the `x-rebel-device-key` request header. Do not include it in event bodies, logs, diagnostics, exports, error messages, or source code.

## HTTP transport

`POST <endpoint>`

Headers:

```text
content-type: application/json
x-rebel-device-key: <private device secret>
```

A request may contain one event or a batch:

```json
{ "kind": "heartbeat", "...": "..." }
```

or

```json
{ "events": [ { "kind": "usage" }, { "kind": "heartbeat" } ] }
```

Current Rebel Core limits are 100 events per request and approximately 2 MB per request. Client queues should remain bounded and batch conservatively.

## Supported event kinds

### `heartbeat`

Purpose: answer whether a program/component is alive, connected, current, or failing.

Recommended fields:

```json
{
  "kind": "heartbeat",
  "program_key": "vector-rebel",
  "program_name": "Vector Rebel",
  "program_category": "rebel",
  "connection_key": "vector-rebel-runtime",
  "name": "Vector Rebel Runtime",
  "type": "browser",
  "component": "PPE helper userscript",
  "status": "connected",
  "version": "2.3.10",
  "source": "Vector Rebel",
  "occurred_at": "2026-09-13T16:00:00.000Z",
  "details": "Concise non-sensitive status text"
}
```

Connection status values: `connected`, `degraded`, `disconnected`, `error`, `unknown`.

If `program_key` is supplied, Rebel Core also updates the Program registry's last-seen/version/health metadata.

### `usage`

Purpose: useful product telemetry such as workflow starts/completions, feature use, update checks, and failures.

Recommended fields:

```json
{
  "kind": "usage",
  "event_key": "vector-rebel:inspection-completed:<stable-id>",
  "program_key": "vector-rebel",
  "program_name": "Vector Rebel",
  "program_category": "rebel",
  "action": "inspection_completed",
  "event_type": "workflow",
  "module": "ppe-inspection",
  "version": "2.3.10",
  "success": true,
  "duration_ms": 12345,
  "occurred_at": "2026-09-13T16:00:00.000Z",
  "source": "Vector Rebel",
  "details": "Concise non-sensitive detail",
  "metadata": {}
}
```

Use a stable `event_key` when the same logical event could be retried. Rebel Core upserts keyed usage events. Events without a key are append-only.

Do not record keystrokes or full arbitrary Vector page content as usage telemetry.

### `suggestion`

Purpose: move Vector Rebel improvement suggestions into Rebel Command instead of managing them on the Vector screen.

Fields include `suggestion_key`, `source_program`, `source_version`, `title`, `content`, `status`, `priority`, `category`, `tags`, `source_context`, and `source`.

Initial status should normally be `new`. Rebel Command owns the management progression:

`new -> reviewing -> accepted/rejected -> implemented`

### `vector_activity`

Purpose: factual Vector work/activity evidence. It does not itself authorize riding-position credit.

Fields may include person/date/time/duration, C-shift flag, assignment group, apparatus, station, duty/activity/pay codes, raw evidence, capture source, verification state, precision segment fields, and notes.

`affects_riding_ratio` must not be set true merely because evidence was captured. Vector Scheduling reconciliation owns that decision.

### `sync_run`

Purpose: report a backfill/import/synchronization run, counts, status, and error details.

### `health_event`

Purpose: durable warning/error/recovery history. Use stable `event_key` values to deduplicate repeated identical failures.

### `scheduling_plan`

Purpose: persist intended future Truck 504 riding assignments independently from actual outcomes.

### `riding_credit`

Purpose: persist verified official ratio ledger entries only. Raw role hints and unreviewed Vector evidence do not qualify.

### `reconciliation_case`

Purpose: surface only ambiguous/missing/partial-day/plan-mismatch/staffing-exception cases that genuinely need review.

## Program keys

Current canonical program keys:

- `vector-scheduling`
- `vector-rebel`
- `rebel-command`
- `rebel-core`

Future Mission Vector Check It programs should receive a stable lowercase key and may register automatically through heartbeat telemetry.

## Health cadence

A two-minute heartbeat is acceptable for active browser tools. Rebel Command currently treats live browser/tool health older than about 15 minutes as degraded and older than about 60 minutes as offline until a new heartbeat arrives.

Avoid emitting durable health-event rows for every heartbeat. Heartbeats update current state; `health_event` is for meaningful changes/errors/recoveries.

## Client reliability requirements

A production client should:

1. keep a bounded local queue;
2. batch events when practical;
3. retry with backoff;
4. use stable event keys for retryable logical events;
5. discard/age out telemetry rather than impairing the Vector tool if an outage is prolonged;
6. never expose the pairing token in diagnostics;
7. tolerate Rebel Core being unavailable;
8. keep operational Vector behavior independent from telemetry success.

## Scheduling implementation status

Vector Scheduling development runtime 0.17.0-dev is the current proving ground. It reports runtime/Tampermonkey health, synchronization state, factual activity, precision segments, verified legacy credits, plans, reconciliation cases, and an idempotent hourly `runtime_loaded` usage event after pairing.

This does **not** mean browser-to-Rebel-Core synchronization is operationally verified. It remains implemented-but-unverified until an authenticated event is observed in Rebel Command from Michael's paired browser.

## Vector Rebel integration rule

Vector Rebel/PPE Helper is safety-sensitive. Integrate this contract as an isolated reporting module without changing the validated PPE decision, submit, verification, or Vector interaction paths. Test with Rebel Core available, unavailable, and invalidly paired before promotion through the normal Mission Vector Check It release process.
