# Known limitations / validation targets

1. **Official API output still needs live validation against this department's data.** The current acquisition utility follows the documented `GET /v1/schedule` structure, but field combinations/qualifiers must be checked against a real export before automatic reconciliation is trusted.
2. **Browser DOM capture is development fallback only.** The new userscript can read the visible schedule/list page and save observations, but the row/container heuristics must be validated against the actual Vector pages and may need selector tuning if Vector changes markup.
3. **Userscript host matching needs live confirmation.** The development build matches CrewSense domains; the exact production hostname(s) used by the department should be confirmed before wider installation.
4. **Duty-code aliases need live validation.** The current engine recognizes `Capt`, `DE-A`, `FFB`, `TM`, `TAC`, `TADE`, `TABC`, `TAFIT`, and `Swing`.
5. **Scenario inference is conservative.** The browser helper can infer TADE-required when the configured engineer is off/elsewhere or appears in an acting-captain role, but nonstandard command coverage remains manually overrideable and should not be trusted blindly.
6. **Nonstandard staffing requires review.** Days where normal command/engineer coverage is absent, replaced, split, or partially covered are not safe to auto-classify from the current rules.
7. **One-firefighter availability is not auto-planned.** With fewer than two tracked firefighters available, the program refuses to invent a complete role set.
8. **No Vector writes.** This is deliberate. A separate explicit authorization would be required before any feature that changes Vector Scheduling is considered.
9. **Private migration data is local-only.** Real crew names, history, observations, API exports and local configuration must not be committed to the public repository.
10. **Recent history may contain unresolved dates.** When the legacy spreadsheet contains raw Vector-report data without explicit position outcomes, those dates remain observations rather than confirmed position credit. Recommendations must remain provisional until gaps are reconciled.
11. **Automatic inference is intentionally conservative.** A firefighter shown as FFB at the home apparatus without a saved plan could be either true Firefighter or Swing/FF; a firefighter shown working elsewhere could be Swing or a staffing move. Both cases require review unless a pre-shift plan supplies the missing intent.
12. **The current scoring model is a fairness optimizer, not a full operational preference model.** Private retrospective workbook validation put the historical assignment within the engine's top three choices in 30 of 32 standard same-assignment two-day blocks tested. The two exceptions show that additional operational factors or human preference may matter; those should be identified before adding any new scoring penalties or weights.
13. **Command duty history is preserved but not optimized.** The five-person migration stores command/engineer/captain duty details for context, but the current recommendation engine balances only the three firefighter rotation categories.
14. **Two-day planning assumes the same planned firefighter roles across both days unless the user deliberately creates a different plan.** Future availability can change between Day 1 and Day 2, so the UI should eventually warn when imported Vector observations differ across the pair before saving a two-day plan.
15. **No automatic background API polling exists yet.** Closed-loop verification currently occurs through imported API probe output or read-only browser capture when Vector pages are opened. Scheduled acquisition belongs in Project X infrastructure/automation only if later authorized and configured, while Mission Vector Check It remains the owner of the scheduling data and logic.
